# AtharvaAi: Complete System Plan (No On-Demand Nodes)

## **Core Philosophy**

```
┌─────────────────────────────────────────────────────────────────┐
│ EVERYTHING RUNS ON SPOT                                         │
│                                                                 │
│ Safety comes from:                                              │
│  • Smart pool selection (ML)                                    │
│  • Diversity across pools (never one basket)                   │
│  • Always-warm substitute (cheapest spot)                       │
│  • Proactive migration (before AWS kills)                      │
│                                                                 │
│ NOT from: expensive on-demand nodes                            │
└─────────────────────────────────────────────────────────────────┘
```

---

## **The Five Layers**

```
LAYER 1: NODE TEMPLATES (User Rules)
  What you define once, rarely change
  
LAYER 2: ML POOL SELECTION (Auto, every 30s)
  What the system picks dynamically
  
LAYER 3: KARPENTER (Auto, real-time)
  How nodes are provisioned and consolidated
  
LAYER 4: RIGHT-SIZING (Auto, daily)
  How pods are optimized to use less
  
LAYER 5: SUBSTITUTE NODE (Always running spot)
  Safety net when anything goes wrong
```

---

## **LAYER 1: Node Templates**

```
PURPOSE:
  Define guardrails for what instances are allowed
  Runs first in pipeline before ML even looks at pools

USER SETS ONCE:
  Architecture:      x64 only (matches container builds)
  Allowed families:  m5, m5a, c5, c5a (trusted families)
  Min size:          large (no tiny nodes)
  Max size:          4xlarge (cost cap)
  Blocked families:  g4 (GPU), m5d (local storage)
  Max interrupt rate: 25% (hard ceiling)

HOW IT FILTERS:
  AWS has 400+ instance types
  After template: ~35 approved types remain
  ML model only evaluates these 35
  Karpenter can only provision these 35

CHANGES WHEN:
  New compliance requirement
  New architecture support (adding ARM)
  Budget changes (adjust max size)
  Otherwise: set and forget
```

---

## **LAYER 2: ML Pool Selection**

```
PURPOSE:
  From 35 template-approved types
  Find top 10 that are safest AND cheapest RIGHT NOW

RUNS: Every 30 seconds

TWO MODELS:
  Classifier → risk score (0-1) per instance type
  Regressor  → savings score (0-1) per instance type

FEATURES FED TO MODELS:
  From web scraper (every 5 min):
    interruption rate per instance type per AZ
    
  From time context:
    hour of day, day of week
    (Tuesday 2pm is safer than Friday 5pm)
    
  From history database:
    how many interruptions in last 24h for this pool
    
  From right-sizing DaemonSet:
    current CPU utilization on these pools
    current memory utilization
    (loaded nodes = riskier)
    
  From AWS pricing API:
    current spot price
    spot vs on-demand ratio
    
  Categorical (one-hot encoded):
    instance family (75 types → 75 features)
    instance size (22 sizes → 22 features)
    availability zone (3 AZs → 3 features)
    Total: 108 features

FILTERING PIPELINE:
  35 template-approved pools
       ↓
  Run classifier → get risk score each
  Filter: remove risk > 0.3 (too risky)
  ~20 pools remain
       ↓
  Check global blacklist (termination events)
  Remove blacklisted pools (12hr TTL)
  ~15 pools remain
       ↓
  Uniqueness filter
  Remove duplicate family+size+AZ combos
  ~12 pools remain
       ↓
  Run regressor → get savings score each
       ↓
  Sort: risk ASC first, then price ASC
  Take top 10
       ↓
  Update Karpenter NodePool with these 10

OUTPUT: Top 10 safe + cheap spot pools
  Updated in Karpenter NodePool every 30 seconds
  Karpenter can ONLY provision from this list
```

---

## **LAYER 3: Karpenter**

```
PURPOSE:
  Provision perfectly-sized nodes from ML-approved list
  Consolidate underutilized nodes automatically

PROVISIONING LOGIC:
  Pod goes Pending
       ↓
  Karpenter reads current NodePool (ML top 10)
       ↓
  Evaluates only those 10 instance types
       ↓
  Bin-packing:
    Sum all pending pod requests together
    Find cheapest instance that fits the sum
    One node for many pods (not one per pod)
       ↓
  Provision that node on that spot pool

CONSOLIDATION LOGIC:
  Runs every 30 seconds
       ↓
  Find nodes with CPU < 30% AND Memory < 30%
       ↓
  Check: can all pods fit on other existing nodes?
       ↓
  If yes:
    Cordon underutilized node
    Drain pods to other nodes
    Delete empty node
       ↓
  Result: fewer nodes, same pods, lower cost

NODE EXPIRY:
  Every node expires after 24 hours
       ↓
  Karpenter provisions fresh replacement
  (from current ML top 10)
       ↓
  Drains old node, deletes it
       ↓
  Why: old spot nodes have higher interruption risk
       Fresh nodes = fresh allocation = safer

DISRUPTION SAFETY:
  Respects PodDisruptionBudgets always
  Max 10% nodes disrupted at once
  No consolidation during peak hours (configurable)
```

---

## **LAYER 4: Right-Sizing**

```
PURPOSE:
  Reduce what pods ask for (requests/limits)
  Based on what they actually use
  Smaller pods → fewer/smaller nodes → less cost

DATA COLLECTION:
  DaemonSet on every node
  Collects every 60 seconds:
    actual CPU used per pod
    actual memory used per pod
    vs what was requested
  Stores in time-series database

ANALYSIS (Daily at 2 AM):
  Per workload (Deployment/StatefulSet):
  
  Pull last 7 days of metrics
  Need 100+ data points minimum
  
  Calculate:
    P95 CPU  = 95th percentile of all readings
    P95 Mem  = 95th percentile of all readings
    P99 CPU  = 99th percentile (for limits)
    P99 Mem  = 99th percentile (for limits)
  
  Recommend:
    new CPU request  = P95 × 1.20 (20% buffer)
    new Mem request  = P95 × 1.25 (25% buffer, OOM risk)
    new CPU limit    = P99 × 1.30
    new Mem limit    = P99 × 1.40
  
  Only recommend if:
    savings > 10% OR waste > 50%
    No OOM kills in last 7 days
    CPU throttling < 20%
    Replica count >= 2

APPLICATION:
  Rolling update (one pod at a time)
  Monitor health at each step
  Auto-rollback if errors detected
  Full rollout: 30-60 minutes

KARPENTER REACTION (Automatic):
  Pods restart smaller after right-sizing
  Nodes now underutilized
  Karpenter detects → consolidates
  Fewer nodes needed → cost drops further

IMPROVEMENT TO ML:
  Right-sizing metrics feed into ML features
  ML knows actual utilization of pools
  Loaded nodes get higher risk score
  Better predictions overall
```

## **LAYER 5: Substitute Node (All-Spot Fallback)**

```
PURPOSE:
  Zero-downtime fallback when:
  • ML model fails
  • Termination notice received
  • Risk score spikes suddenly
  All without any on-demand nodes

HOW IT'S SELECTED:
  
  Scan all workloads → find largest pod requirements
  Example: worker needs 1.0 CPU, 2.5GB
  
  Substitute must fit 2 replicas of largest:
  Min: 2.0 CPU, 5.0GB (+ 20% overhead = 2.4 CPU, 6GB)
  
  Apply template rules (architecture, families, sizes)
  Apply basic stability filter:
    Historical interruption rate < 15%
    Not blacklisted in last 7 days
    Available in at least 2 AZs
  
  Pick cheapest that passes all filters
  Result: t3a.large or m5a.large (cheapest stable spot)
  
  NOT selected by ML (independent system)
  NOT managed by Karpenter (static, always running)
  Re-evaluated weekly (not real-time)

NORMAL STATE (ML working fine):
  Substitute holds placeholder pods
  Placeholder: lowest priority class, 10m CPU, 32Mi RAM
  Fills ~30% of node capacity
  All production images pre-pulled and cached
  Networking pre-configured
  Readiness: instant (0 seconds)

SUBSTITUTE IS SPOT BUT SAFE BECAUSE:
  Uses historically stable pool (< 15% interruption)
  Different pool from ML-chosen nodes (diversity!)
  If substitute gets terminated too:
    Its pods (low priority placeholders) are already gone
    Or: real pods moved to ML nodes (reverse fallback)
  Different AZ from primary nodes (geo-diversity)
```

## **Termination Notice Flow (No On-Demand)**

```
T+0s:   AWS sends termination notice
        Node affected: ML-chosen spot node
        Time remaining: 120 seconds

T+2s:   DaemonSet detects notice
        Event sent to decision engine

T+3s:   Decision engine checks substitute
        Substitute: available and healthy ✅

T+5s:   TWO PARALLEL ACTIONS:

        ACTION A (Immediate):          ACTION B (Parallel):
        Cordon affected node           Provision new spot node
        Evict placeholder pods         from current ML top 10
        from substitute                (starts booting now)
        Move real pods →
        substitute node

T+15s:  Real pods running on          New spot node: booting
        substitute ✅                  (3-5 min to ready)
        Zero downtime!

T+90s:  Affected node fully drained
T+120s: AWS terminates affected node

T+300s: New ML-chosen spot node ready
        Begin gradual migration:
        substitute → new node
        25% pods at a time
        5 min between batches

T+420s: All pods on new ML spot node ✅
        Substitute returns to standby
        Placeholder pods refill substitute
        
        Terminated pool flagged globally:
        All other clients warned
        Pool removed from everyone's top 10
        12-hour blacklist in Redis

TOTAL DOWNTIME: 0 seconds ✅
FULL RECOVERY: ~7 minutes
```

## **ML Failure Flow (No On-Demand)**

```
ML FAILURE DETECTION:
  Health check every 30 seconds:
  
  Check 1: Can model run inference? (test data)
    No response in 5s → FAIL
  
  Check 2: Are predictions reasonable?
    All same value → model stuck → FAIL
  
  Check 3: NodePool updating?
    Last update > 5 minutes ago → FAIL
  
  Check 4: Scraper working?
    Data > 15 minutes old → PARTIAL FAIL

PARTIAL FAIL:
  Use last known good ML output (cached)
  Valid for up to 30 minutes
  Alert team, do not activate substitute yet

FULL FAIL:
  Activate substitute immediately
  
  What changes:
    Karpenter NodePool: add substitute type to list
    New pods: prefer substitute node
    Existing pods: stay on current nodes (don't move yet)
    
  What stays same:
    Existing ML-chosen nodes keep running
    Pods already running: zero disruption
    Substitute: absorbs new pods only
  
  Why not move everything immediately:
    Existing pods are fine (ML failure doesn't affect them)
    Only new pods or evicted pods need somewhere to go
    No need to cause disruption

ML RECOVERY:
  Team fixes pipeline
  5 consecutive successful health checks pass
  Enter cooldown (20 minutes)
  Validate ML output is reasonable
  Gradually restore ML control
  Substitute returns to standby
```

---

## **Cooldown & Recovery Logic**

```
TRIGGER: Incident resolved (termination handled OR ML recovered)

PHASE 1: STABILIZATION (0-10 minutes)
  Do nothing
  Let system settle
  Monitor for secondary issues
  Reason: Rapid changes after incident cause instability

PHASE 2: VALIDATION (10-20 minutes)
  ALL must pass before migration begins:
  
  ✓ ML running 5 consecutive successful inferences
  ✓ New node Ready for 5+ consecutive minutes
  ✓ Terminated pool absent from ML top 10
  ✓ Substitute stable (no pod restarts)
  ✓ Global blacklist active for terminated pool
  
  Any fail: reset to Phase 1, wait another 10 min

PHASE 3: GRADUAL MIGRATION (20-40 minutes)
  Move 25% of pods from substitute → new ML node
  Wait 5 minutes, monitor:
    Error rate unchanged?
    Latency unchanged?
    No pod restarts?
    
  If healthy: move next 25%
  If issues: pause, investigate, revert if needed
  
  4 batches × 5 minutes = 20 minutes total

PHASE 4: RETURN TO NORMAL (40+ minutes)
  All pods on ML-chosen spot nodes
  Substitute: placeholder pods refilled
  Substitute: back to standby state
  
  Post-incident actions:
    Log full incident timeline
    Record which pool was terminated
    Feed termination data to ML training pipeline
    Update global pool history database
    Improve next model version
```

# Direct Migration: Risk/Price Threshold Breach Logic

## **The Distinction: Two Different Scenarios**

```
┌─────────────────────────────────────────────────────────────────┐
│ SCENARIO A: TERMINATION NOTICE (2-min window)                  │
│   → Use substitute node (instant landing, no time to provision)│
│                                                                 │
│ SCENARIO B: RISK/PRICE THRESHOLD BREACH (no time pressure)     │
│   → Spin up new ML-chosen node directly                        │
│   → No substitute needed (we have TIME to provision properly)  │
│   → Substitute stays in standby                                │
└─────────────────────────────────────────────────────────────────┘

KEY INSIGHT:
  Substitute exists for EMERGENCY (2-min window)
  Threshold breach is PROACTIVE (we chose to act)
  When we choose to act, we have time to do it right
  No need to use substitute as middle step
```

---

## **What Triggers Direct Migration**

```
TWO THRESHOLDS THAT TRIGGER DIRECT MIGRATION:

THRESHOLD 1: RISK SCORE BREACH
  Configured by user (default: 0.6)
  
  ML classifier output per pool:
  risk_score < 0.3  → safe zone, do nothing
  risk_score 0.3-0.6 → watch zone, monitor closely
  risk_score > 0.6  → BREACH → trigger direct migration
  risk_score > 0.8  → CRITICAL → urgent direct migration

THRESHOLD 2: PRICE THRESHOLD BREACH
  Configured by user (default: 20% above baseline)
  
  price_baseline = average price over last 7 days
  current_price > baseline × 1.20 → BREACH
  current_price > baseline × 1.50 → CRITICAL BREACH
  
  Example:
  Baseline: $0.085/hr for m5a.large
  Threshold: $0.085 × 1.20 = $0.102/hr
  Current:   $0.115/hr → BREACHED → trigger migration

COMBINED SCORE:
  System can also trigger on combined condition:
  risk_score > 0.4 AND price > baseline × 1.15
  (medium risk + medium price spike = still migrate)
  
  Logic: neither alone is critical
  but together they signal pool degradation
```

## **Threshold Configuration Logic**

```
USER CONFIGURES PER CLUSTER:

RISK THRESHOLDS:
  watch_threshold:   0.3  (start monitoring closely)
  breach_threshold:  0.6  (trigger direct migration)
  critical_threshold: 0.8  (urgent migration, less delay)

  At critical: confirmation reduced to 1 reading (not 3)
  Too risky to wait 90 seconds

PRICE THRESHOLDS:
  watch_threshold:   15% above baseline
  breach_threshold:  20% above baseline
  critical_threshold: 50% above baseline

CONFIRMATION READINGS:
  Normal breach (risk 0.6-0.8 OR price 20-50%):
    3 consecutive readings (90 seconds)
  
  Critical breach (risk > 0.8 OR price > 50%):
    1 reading (immediate action)
    Too risky to wait for confirmation

BASELINE CALCULATION FOR PRICE:
  Rolling 7-day average of spot price for this pool
  Recalculated daily
  Accounts for normal price fluctuation
  Only flags genuine spikes not normal variance

SMART THRESHOLD ADJUSTMENT:
  System learns your cluster patterns
  If your cluster always runs at night:
    Thresholds slightly relaxed during business hours
    (less traffic = can tolerate brief disruption)
  If peak business hours:
    Thresholds tightened
    (migrate earlier to avoid any risk during peak)
```

## **What Makes This Different from Substitute Flow**

```
COMPARISON:

SUBSTITUTE FLOW (Termination Notice):
  Trigger:    AWS forces it (2-min window)
  Time:       120 seconds to act
  Strategy:   Move first, provision later
  Substitute: ACTIVATED (instant landing needed)
  Downtime:   0 seconds (substitute absorbs immediately)
  
  Order: Move pods → substitute → provision new → migrate back

DIRECT MIGRATION FLOW (Threshold Breach):
  Trigger:    System chooses to act (proactive)
  Time:       Minutes available (no AWS forcing)
  Strategy:   Provision first, move after
  Substitute: NOT ACTIVATED (stays in standby)
  Downtime:   0 seconds (new pod starts before old stops)
  
  Order: Provision new → validate → migrate direct → decommission old

WHY NO SUBSTITUTE NEEDED IN BREACH:
  
  Substitute solves: "I have 120 seconds, no time to provision"
  Threshold breach: "I have 3-15 minutes, time to provision properly"
  
  Using substitute in breach scenario:
    Move to substitute → then move again to ML node
    = Double migration (unnecessary disruption)
    = Two rolling updates instead of one
    = Waste of pod restarts
    
  Direct migration:
    One clean move: old pool → new ML pool
    Single rolling update
    No intermediate hop
    Cleaner, faster, less disruption
```

## **Edge Cases**

```
EDGE CASE 1: New node not available during provisioning
  
  Scenario: Karpenter tries to provision m5.large-us-west-2b
  AWS responds: no capacity in this AZ
  
  Fallback logic:
    Pick #2 from ML top 10 (different pool)
    Try provisioning that
    If that fails: try #3
    Continue down top 10 list
    
    If ALL top 10 fail to provision:
      THEN activate substitute (last resort)
      This is the only time substitute activates for breach
      Alert team: spot capacity issue in region

EDGE CASE 2: Risk score recovers during confirmation wait
  
  Scenario:
  T+0s:  risk = 0.72 (breach)
  T+30s: risk = 0.68 (still breach)
  T+60s: risk = 0.28 (recovered!)
  
  Action: Cancel migration process
  Do not provision new node (waste of resources)
  Reset confirmation counter
  Continue monitoring
  
  Why this matters:
  Spot prices/risks can spike and recover quickly
  90-second confirmation prevents chasing false signals
  Saves unnecessary migration and provisioning cost

EDGE CASE 3: New pool breaches WHILE migrating
  
  Scenario:
  Started migrating to m5.large-us-west-2b (looked safe)
  50% pods moved
  m5.large-us-west-2b risk score jumps to 0.75 (breach!)
  
  Action:
    Pause migration immediately
    Stop moving more pods
    Re-run ML selection (pick new top 1)
    Provision third node (new ML choice)
    Validate third node
    Move remaining 50% from old node → third node
    Also move already-migrated 50% → third node
    
  Result: Three nodes temporarily, then one clean node
  Slightly more disruption but still zero downtime

EDGE CASE 4: Both risk AND price breach simultaneously
  
  Action: Use critical threshold rules
  Single confirmation reading (not 3)
  Immediate provisioning
  Faster batch migration (10% at a time, less wait)
  Priority escalated in Karpenter

EDGE CASE 5: All pools in top 10 breach simultaneously
  
  Scenario: Regional AWS issue, all spot pools risky
  
  Action:
    Substitute node activated (only time for breach scenario)
    Move all pods to substitute immediately
    Alert team: regional spot issue
    Wait for ML to find safe pools in different AZ
    Once found: direct migrate from substitute → new pool
    
  This is genuine emergency, substitute justified here
```

## **Summary: The Clean Logic**

```
THRESHOLD BREACH = PROACTIVE DECISION = TIME AVAILABLE

Because we have time:
  1. Confirm it's real (90 seconds, 3 readings)
  2. Provision new node FIRST (ML-chosen, best pool)
  3. Validate new node is healthy
  4. Migrate pods directly (old → new, no middle hop)
  5. Delete old node
  6. Done. Substitute never needed.

SUBSTITUTE ONLY ACTIVATES FOR:
  ✓ AWS termination notice (120-second emergency)
  ✓ ALL top 10 pools unavailable (regional outage)
  ✓ ML complete failure + breach happening simultaneously
  
  Everything else: direct migration, cleaner and faster

RESULT:
  Risk breach:  0 downtime, single migration, ~11 minutes
  Price breach: 0 downtime, single migration, ~11 minutes  
  Substitute:   stays warm and ready for real emergencies
  System:       always on optimal pool, always cost-efficient
```
