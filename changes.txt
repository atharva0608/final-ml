Here are the detailed, non-code functional instructions to implement **Role-Based Dashboard Customization** with persistent user preferences. This approach shifts your dashboard from a hard-coded layout to a dynamic, widget-based system driven by database configuration.

### Phase 1: Database & Backend Architecture

You need to store *how* a user wants to see their dashboard. Instead of creating complex new tables, you can leverage the existing `User` model.

**1. Update the User Model**

* **Schema Change:** Add a new column to your `User` table (e.g., `preferences` or `dashboard_config`).
* **Data Type:** Use a **JSON/JSONB** type. This allows flexibility to store layout arrays, theme choices, or widget settings without changing the schema again later.
* **Migration:** Create a database migration script to add this column to existing users, defaulting to `NULL` or an empty object `{}`.

**2. API Endpoints for Preferences**

* **Update `GET /auth/me` (or User Profile):** Ensure the login/profile response includes this new `preferences` object so the frontend has it immediately upon loading.
* **Create `PATCH /users/me/preferences`:**
* **Input:** Accepts a JSON object (e.g., `{ dashboard_layout: [...] }`).
* **Logic:** Updates the logged-in user's record in the database.
* **Validation:** Ensure the user isn't trying to inject settings for restricted widgets (e.g., a "Member" trying to enable "Global Revenue" widget).



### Phase 2: Frontend Component Architecture

Refactor the monolithic `Dashboard.jsx` into a modular "Widget Engine".

**1. Create a "Widget Registry"**

* Define a central directory of all available dashboard components (Widgets).
* **Break Down Existing Components:** Extract parts of your current dashboard into small, standalone files:
* `CostKPICard`
* `SavingsChart`
* `ClusterHealthMap`
* `ActivityFeed`
* `PendingApprovalsCard` (New for Team Leads)
* `PlatformHealthMetrics` (New for Super Admins)


* **Registry Map:** Create a mapping object where string keys point to these components.
* *Example:* `'kpi_cost': <CostKPICard />`



**2. Define Default Role Layouts**

* Create a configuration constant file (e.g., `roleDefaults.js`).
* Define the "Standard Layout" for each `UserRole`:
* **SUPER_ADMIN:** `['platform_health', 'tenant_list', 'global_audit', 'revenue_chart']`
* **ORG_ADMIN:** `['net_savings', 'current_spend', 'savings_projection', 'cluster_map']`
* **TEAM_LEAD:** `['team_budget', 'pending_approvals', 'team_activity', 'member_list']`
* **MEMBER:** `['my_active_resources', 'my_tickets', 'recent_logs']`



### Phase 3: The Dynamic Dashboard Logic

Update the main `Dashboard` page to render based on data, not hard-coded JSX.

**1. The Loading Sequence**

* **Step A:** When the dashboard loads, check the user's `preferences.dashboard_layout` from the store/API.
* **Step B:** If it exists, use that array of widget keys.
* **Step C:** If it is `null` (first time login), look up the `UserRole` in your `roleDefaults` file and use that array.

**2. The Rendering Engine**

* Instead of writing `<KPICard />` directly, map over the list of widget keys.
* For each key, look it up in the **Widget Registry** and render the corresponding component.
* **Safety Check:** If a key exists in preferences but not in the registry (e.g., feature removed), skip it gracefully to prevent crashes.

### Phase 4: User Customization Features

Give users the UI to change their view.

**1. "Customize Dashboard" Mode**

* Add a button (e.g., "Edit Layout") to the dashboard header.
* When clicked, switch the dashboard to **Edit Mode**.
* **Visual Cues:** Add borders or "drag handles" to widgets to indicate they are editable.

**2. The Customization Toolbar/Drawer**

* **Toggle Visibility:** Show a list of *all available widgets* for that user's role with checkboxes.
* *Constraint:* Filter this list by role. Do not show "Platform Health" in the list for an Org Admin.


* **Reorder (Optional):** Allow users to drag and drop widgets to change their order, or provide "Move Up/Down" buttons.

**3. Saving Changes**

* When the user clicks "Save Layout":
1. Capture the current list of active widget keys.
2. Send this list to the `PATCH /users/me/preferences` endpoint.
3. Update the local state/store immediately to reflect changes without reloading.



### Summary of Data Flow

1. **Login:** Backend sends `user.role = 'ORG_ADMIN'` and `user.preferences = null`.
2. **Dashboard Load:** Frontend sees `null` preferences. Loads `ORG_ADMIN_DEFAULTS` (Cost, Savings, Clusters).
3. **User Action:** User clicks "Edit", hides "Cluster Map", adds "Recent Activity". Clicks Save.
4. **API Call:** `PATCH` sends `{ dashboard_layout: ['cost', 'savings', 'activity'] }`.
5. **Next Login:** Backend sends the saved layout. Frontend renders exactly what the user saved.
